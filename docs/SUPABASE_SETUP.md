# Подключение QuestTask к Supabase

Инструкция ниже предназначена для **нового отдельного проекта**. Текущий проект QuestTask уже создан и подключён локально: базовая миграция и миграция челленджей применены, повторно выполнять их нельзя. Миграции магазина и админ-панели подготовлены, но к текущему проекту ещё не применены. 19 ноября SMTP переключён с тестового Resend на Яндекс Почту `questtask@yandex.ru`; установлен русский шаблон с кодом. Тестовое письмо Supabase дошло до ящика Яндекса. 22 ноября подтвердилось, что письма на тестовый Gmail доставлялись в «Спам», а после отметки «Не спам» новое письмо пришло во «Входящие».

## 1. Создать проект

Откройте [Supabase Dashboard](https://supabase.com/dashboard), войдите в свою учётную запись и создайте проект QuestTask. Сохраните пароль базы у себя; он не понадобится клиентскому приложению. Дождитесь готовности БД.

Найдите Project URL и публичный Publishable key (либо legacy anon key) в настройках API проекта. Не копируйте service_role, Secret key или пароль PostgreSQL в приложение.

## 2. Применить схему

В SQL Editor нового проекта последовательно выполните под владельцем БД всё содержимое файлов `supabase/migrations/202611170001_tasks_foundation.sql`, `202611220001_challenges.sql`, `202611220002_shop.sql` и `202611220003_admin.sql`. Каждый скрипт включает транзакцию; при ошибке остановитесь и разберите её перед следующим скриптом. Повторно на уже созданных таблицах их запускать не нужно. В текущем проекте QuestTask нужны только последние два скрипта.

В public появятся profiles, tasks, challenges, completed_challenges, shop_items, purchases и user_inventory, в private — operations, economy_events и admin_audit. Схему private не добавляйте в список схем Data API. Приложению не нужно давать прямые права записи: они намеренно отозваны. Профиль создаётся триггером при регистрации; игровые и административные изменения выполняются через RPC.

Для проверки состава схемы в SQL Editor:

```sql
select schemaname, tablename, rowsecurity
from pg_tables
where schemaname in ('public', 'private')
  and tablename in ('profiles', 'tasks', 'challenges', 'completed_challenges', 'shop_items', 'purchases', 'user_inventory', 'operations', 'economy_events', 'admin_audit');
```

У всех десяти таблиц rowsecurity должен быть true. Не применяйте DDL из первоначального PDF: он открывает небезопасные права, исправленные в ТЗ 2.0.

## 3. Настроить email-подтверждение

В Authentication включите провайдер Email и обязательное подтверждение email. Минимальная длина пароля — 8 символов. В текущем проекте сохранена длина кода Supabase — 8 цифр, срок установлен в 600 секунд; форма приведена к этим параметрам. Это отклонение от 6 цифр в ТЗ 2.0, зафиксированное при подключении. Интервал повторной отправки — не менее 60 секунд; интерфейс уважает серверный rate limit.

В текущем интерфейсе Supabase Free шаблон нельзя изменить до настройки собственного SMTP. После настройки в Email Templates → Confirm signup поместите содержимое `supabase/templates/confirm-signup.html` или краткий вариант:

```html
<h2>Добро пожаловать в QuestTask</h2>
<p>Код подтверждения:</p>
<p style="font-size: 28px; letter-spacing: 6px">{{ .Token }}</p>
<p>Код действует 10 минут. Если вы не регистрировались, проигнорируйте письмо.</p>
```

Используется именно Token, а не ConfirmationURL. Клиент вызывает verifyOtp с type='email' согласно текущему официальному примеру. Настройки длины/срока кода и реальный сценарий обязательно проверьте на своём проекте. [Шаблоны Supabase](https://supabase.com/docs/guides/auth/auth-email-templates), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp).

В URL Configuration текущий Site URL — `http://127.0.0.1:5173`. Используйте этот адрес для локальной работы. Здесь после настройки шаблона подтверждение вводится вручную. После публикации задайте фактический адрес сайта и удалите ненужные адреса из рабочего окружения.

## 4. Подключить доставку через Яндекс Почту

Для учебного проекта без собственного домена можно отправлять письма через отдельный ящик Яндекс Почты. В настройках ящика откройте «Почтовые программы», включите IMAP и «Пароли приложений и OAuth-токены», сохраните изменения. В Яндекс ID создайте пароль приложения типа «Почта». Он даёт доступ к IMAP, POP3 и SMTP; храните его только в серверных настройках Supabase. По [справке Яндекса](https://yandex.ru/support/id/ru/authorization/app-passwords.html) новый пароль может начать действовать через 2–3 часа.

В Supabase Custom SMTP задайте:

| Параметр | Значение |
| --- | --- |
| Sender email | `questtask@yandex.ru` (или адрес своего ящика) |
| Sender name | QuestTask |
| Host | `smtp.yandex.ru` |
| Port | 465, SSL |
| Username | `questtask` (для адреса `questtask@yandex.ru` — часть до `@`) |
| Password | Пароль приложения «Почта», не обычный пароль Яндекс ID |

Проверка на адресе Яндекса и тестовом Gmail прошла; Gmail поместил письма Яндекса в «Спам». Для других провайдеров доставку нужно проверить отдельно. Если Auth возвращает 500, откройте Logs → Auth: ошибка SMTP 535 означает, что Яндекс отклонил логин или пароль. Сначала проверьте логин, настройки почтовых программ и дождитесь активации нового пароля. [Инструкция по SMTP](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others.html).

### Альтернатива: Resend с собственным доменом

Для регистрации произвольных пользователей нужен собственный подтверждённый домен отправителя. В Resend подтвердите домен по предложенным DNS-записям и создайте API-ключ с правами отправки.

В Supabase Custom SMTP задайте:

| Параметр | Значение |
| --- | --- |
| Sender email | Адрес на подтверждённом домене, например questtask@ваш-домен |
| Sender name | QuestTask |
| Host | smtp.resend.com |
| Port | 465, TLS |
| Username | resend |
| Password | API-ключ Resend |

Ключ остаётся в серверных SMTP-настройках. Отправитель onboarding@resend.dev пригоден только для ограниченного теста на собственный адрес Resend; это не вариант для регистрации любых пользователей. Не рассчитывайте на алиасы email как на обход ограничения. [SMTP Resend](https://resend.com/docs/send-with-smtp), [ограничения resend.dev](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).

Если домена ещё нет, Resend с `onboarding@resend.dev` годится только для прежнего ограниченного теста. Реальную регистрацию считать готовой до успешного получения OTP через выбранный SMTP нельзя.

## 5. Заполнить локальные настройки

Из папки quest-task:

```powershell
Copy-Item .env.example .env.local
```

Откройте `.env.local` в редакторе:

```dotenv
VITE_SUPABASE_URL=https://идентификатор-проекта.supabase.co
VITE_SUPABASE_ANON_KEY=ваш_публичный_publishable_или_anon_ключ
VITE_BASE_PATH=/
```

Остановите прежний сервер Ctrl+C и запустите `pnpm dev` или `start-dev.cmd`. Перезагрузка вкладки без перезапуска Vite недостаточна для изменения env. Поля входа станут доступны, если URL и ключ заданы.

## 6. Первый настоящий сценарий

1. Зарегистрируйтесь с никнеймом и реальным доступным email.
2. Получите код, введите его; убедитесь, что открыт аккаунт с нулевым балансом.
3. Создайте сложную задачу и завершите её. Ожидается 50 XP и 30 монет.
4. Обновите страницу: задача и баланс должны сохраниться.
5. Удалите завершённую задачу: баланс не изменится.
6. Выйдите и снова войдите с email/паролем: данные должны быть прежними.
7. Проверьте второй аккаунт: он не видит задачи и профиль первого.
8. Проверьте неверный и истёкший OTP, повторную отправку и обрыв сети. При неопределённом результате задачи используйте «Повторить запрос».

Обычному игроку роль администратора не нужна. Демонстрационные кнопки не заменяют этот сценарий, поскольку демонстрация никогда не использует Supabase.

## Первый администратор

После применения всех четырёх миграций найдите нужную учётную запись в **Authentication → Users** и убедитесь, что её email подтверждён. В файле `supabase/bootstrap/first_admin.sql` замените нулевой UUID на `auth.users.id` этой записи и выполните скрипт **один раз** в SQL Editor под владельцем БД. Скрипт отклонит неподтверждённого пользователя, отсутствие профиля или попытку назначить второго первого администратора. Не добавляйте реальный UUID или email в Git.

После назначения войдите заново: ссылка «Админ» откроет список игроков, челленджей и товаров. Новые челленджи и товары публикуются через RPC; опубликованные записи архивируются вместо редактирования. Смена роли и сброс прогресса требуют подтверждения в интерфейсе. Сброс создаёт новую игровую эпоху, снимает активный титул и сохраняет прежнюю историю для аудита.

## 7. Конкурентный тест

Создайте отдельного подтверждённого тестового игрока. В `.env.test.local` сохраните TEST_SUPABASE_URL, TEST_SUPABASE_ANON_KEY, TEST_EMAIL и TEST_PASSWORD. Этот файл игнорируется Git, публиковать его нельзя.

```powershell
node --env-file=.env.test.local --test tests/live/concurrency.test.mjs
```

Тест одновременно отправляет 10 запросов выполнения одной задачи. Должен пройти ровно один, девять возвращают TASK_ALREADY_COMPLETED; общий прирост — 50 XP / 30 монет. В конце задача архивируется, награда остаётся у тестового игрока.

Если возникает permission denied, не открывайте таблицы для записи: проверьте полноту миграции и вызов нужного RPC. Если профиль отсутствует, проверьте регистрационный триггер; существующие до миграции пользователи автоматически не переносятся. Если письмо не приходит, проверьте Auth logs, настройки отправителя и лимиты выбранного почтового провайдера.
