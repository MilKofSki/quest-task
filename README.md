# QuestTask

React/Vite-приложение по ТЗ 2.0. Реализованы вход и регистрация с email OTP, личные задачи, три сложности, фильтры, пагинация, однократные награды, архивирование, челленджи и локальная демонстрация. Серверная часть поставляется SQL-миграциями для Supabase.

**Supabase подключён локально (18 ноября 2026).** Обе миграции применены к проекту QuestTask; RLS и запреты анонимного чтения проверены в облаке. Публичный publishable key сохранён в игнорируемом `.env.local`. 19 ноября SMTP переключён на Яндекс Почту `questtask@yandex.ru`: письмо с кодом дошло до ящика Яндекса. 22 ноября проверено, что письма на тестовый Gmail доставляются; сначала они попадали в «Спам», а после отметки «Не спам» контрольное письмо пришло во «Входящие». Создание и завершение сложной задачи, награда 50 XP / 30 монет и сохранение после обновления страницы проверены на облаке. Челленджи проверены локальными SQL-тестами, демосценарием и чтением данных из облака. Параллельные запросы подтверждённого игрока ещё требуют отдельного теста. Магазин, инвентарь и админ-панель относятся к следующим этапам.

## Быстро открыть на этом компьютере

Запустите `start-dev.cmd` двойным щелчком из папки проекта. Скрипт использует установленный Node.js либо уже имеющийся runtime Codex и открывает локальный сервер. Откройте адрес, напечатанный Vite, обычно http://127.0.0.1:5173/, и нажмите **«Попробовать демо»**. Закрытие окна сервера останавливает приложение.

Демо работает в памяти, без сетевых обращений к БД; выход или перезагрузка страницы начинают его заново. Исходный баланс — 0 XP / 0 монет. Выполнение задачи «Закончить важный проект» даёт 50 XP и 30 монет. Настоящие данные после подключения будут храниться в Supabase.

## Запуск на другом компьютере

Нужен Node.js 22.12+ (поддерживаемая LTS-версия) и pnpm 11.25.0. Сборка и тесты здесь проверены на Node.js 24.22.3.

```powershell
npm install --global pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm dev
```

Если PowerShell блокирует `pnpm.ps1`, используйте `pnpm.cmd` вместо `pnpm`; изменять политику безопасности системы не требуется. В проекте используется `pnpm-lock.yaml`; не создавайте второй lock-файл через `npm install`.

## Подключение настоящих аккаунтов

Следуйте [пошаговой инструкции](docs/SUPABASE_SETUP.md). Основные действия:

1. Создать новый проект Supabase.
2. Последовательно применить обе SQL-миграции из `supabase/migrations/`.
3. Включить подтверждение email и настроить отправку кода.
4. Скопировать `.env.example` в `.env.local`, вписать URL и публичный ключ, перезапустить сервер.
5. Зарегистрировать тестового игрока и пройти проверочный сценарий из инструкции.

Пароль БД, service_role/secret key и пароль SMTP в `.env.local` клиента не нужны. Все `VITE_*` значения становятся публичными в сборке. Название `VITE_SUPABASE_ANON_KEY` принимает публичный legacy anon key или publishable key.

## Команды

```powershell
pnpm dev             # Локальная разработка
pnpm test            # SQL-тесты обеих миграций на PGlite
pnpm build           # Production-сборка в dist
pnpm preview         # Просмотр production-сборки
pnpm test:live       # Реальная конкурентность на отдельном тестовом Supabase
```

Проверка доступности Auth и запрета анонимного чтения без создания данных:

```powershell
node --env-file=.env.local --test tests/live/public-access.test.mjs
```

Live-тест пропускается, пока не заданы TEST_SUPABASE_URL, TEST_SUPABASE_ANON_KEY, TEST_EMAIL и TEST_PASSWORD. Он использует отдельного подтверждённого тестового игрока, начисляет ему 50 XP / 30 монет и архивирует созданную задачу. Не запускайте его на личном или рабочем аккаунте.

Для локального файла с тестовыми реквизитами `.env.test.local` (игнорируется Git):

```powershell
node --env-file=.env.test.local --test tests/live/concurrency.test.mjs
```

PGlite исполняет SQL PostgreSQL, но тестовая схема Auth эмулируется и запросы идут через одно соединение. Эти тесты проверяют права, RLS, транзакционный откат и идемпотентность, но **не доказывают конкурентность облачной БД или работу Supabase Auth**. Для этого предназначены live-тест и ручная проверка OTP.

## Где что находится

- `src/components/` — экран авторизации, задачи и челленджи.
- `src/api/tasks.js` — чтение данных, RPC, сохранение ожидающего запроса.
- `src/demo/adapter.js` — изолированная демонстрация.
- `src/hooks/useTasks.js` — загрузка, фильтры, повтор запроса и обновление состояния.
- `supabase/migrations/` — схема, RLS, права, регистрационный триггер, игровые RPC.
- `tests/` — SQL-тесты и облачная проверка конкурентности.
- `docs/VERIFICATION.md` — локальный отчёт о проверках с данными тестового аккаунта; исключён из публичного репозитория.

## Как устроено начисление

Клиент вызывает `complete_task`. Сервер проверяет подтверждение email, владельца и текущую игровую эпоху; блокирует профиль и задачу; проверяет completed_at. Выполнение, баланс, запись операции и событие награды сохраняются в одной транзакции. Прямые изменения таблиц из браузера запрещены.

У каждого действия есть request_id. При потере соединения запрос остаётся в localStorage под ключом конкретного аккаунта; кнопка «Повторить запрос» отправляет тот же ключ. Повтор уже выполненной операции возвращает её результат без нового эффекта. Ожидающие операции другого аккаунта не отправляются. localStorage не является источником прав: сервер заново проверяет все параметры.

Удаление задачи — архивирование. Награды и история завершения сохраняются. Миграция уже содержит progress_epoch, но сам административный сброс будет добавлен на следующем этапе.

## GitHub Pages

Рабочий процесс `.github/workflows/deploy.yml` запускает тесты при отправке изменений в `main`. Сборка и публикация `dist` включаются переменной репозитория `ENABLE_PAGES=true` после готовности сайта к публичному запуску. Для обычного репозитория workflow задаёт Vite путь `/<имя-репозитория>/`. Маршруты приложения используют `HashRouter`, поэтому обновление вложенной страницы работает на статическом хостинге.

Перед публичным запуском откройте **Settings → Secrets and variables → Actions → Variables** и добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` из текущего проекта Supabase, затем `ENABLE_PAGES=true`. Это публичные параметры клиентского приложения; пароли БД, SMTP и `service_role` в GitHub не добавляйте. В **Settings → Pages** выберите **GitHub Actions** как Source и отправьте ветку `main` либо запустите workflow вручную. Адрес страницы будет в результате задания `deploy`; укажите его как **Site URL** в Supabase Auth. Локальный адрес сохраните среди разрешённых Redirect URLs для разработки. SQL-миграции выполняются отдельно и не запускаются при публикации сайта.

Если репозиторий называется `<имя-пользователя>.github.io` или используется собственный домен в корне, замените `VITE_BASE_PATH` в workflow на `/`. Репозиторий создан; GitHub Pages пока выключен.
